## II. The Problem with Traditional Tickets

Most software teams work like this:

1. A JIRA ticket is created.
2. Requirements are written in vague prose.
3. The ticket is assigned to a developer.
4. The developer interprets the requirements.
5. The developer builds the feature.
6. The feature is reviewed.
7. The feature is tested.
8. The feature is deployed.

This process takes days. Sometimes weeks. Sometimes months.

And throughout this process, the team has no shared understanding of what the feature _actually does_. They have a shared understanding of what the ticket _says_. But that is not the same thing.

The ticket is a description. The description is an abstraction. The abstraction is a ghost.

---

## III. The Essence-in-Docs Practice

The Essence-in-Docs practice solves this problem.

When a tech task is created in JIRA, the developer creates an **essential implementation right there in the docs**.

A simple HTML page. With vanilla JavaScript. With JSDoc comments.

No frameworks. No dependencies. No infrastructure.

Just the substance.

---

## IV. What Is the Essence?

The essence is the **pure, synchronous, in-memory representation of the feature**.

It includes:

- **UI elements** — bare-bone HTML that shows what the user sees.
- **State logic** — simple JavaScript that tracks the state transitions.
- **Transformations** — pure functions that process data.
- **Integration with IO** — mock interactions, generated from Swagger schemas if backend is involved.

The essence is not the final implementation. It is not React. It is not a database. It is not an API.

The essence is what the feature _is_. It is the communicated idea. It is the substance.

---

## V. How It Works

**Step 1: The Ticket Is Created**

A tech task is created in JIRA. The developer receives it.

**Step 2: The Essence Is Built**

The developer opens an HTML page directly inside the JIRA ticket (using a JIRA plugin that allows custom HTML with script execution).

They build the essence:

- HTML elements for the UI.
- JavaScript for the state logic.
- JSDoc comments for clarity.
- Mock IO functions for integration.

This takes under an hour. Sometimes less.

**Step 3: The AI Assists**

We use AI to accelerate this process. We still write the code ourselves—AI is just a tool that makes it faster and easier.

Ideally, we follow a TDD format. We write the test first, then the implementation. Step by step. The essence emerges from the tests.

**Step 4: The Essence Is Shared**

The team can now see and interact with the feature directly in the JIRA ticket.

They can click the buttons. They can type in the fields. They can see the state transitions. They can test the logic.

The ticket is no longer just text. It is a working implementation.

**Step 5: The Essence Serves as Reference**

The essence becomes the reference for the final implementation.

When the developer builds the real feature, they use the essence as a guide. They know exactly what the substance is. They only need to add the accidents—the framework, the database, the deployment.

## VI. The Benefits

**Instant Feedback**

The team can see and interact with the feature within an hour. They can test it. They can validate it. They can correct it.

No more waiting until the feature is "finished" to discover that it was built wrong.

**Shared Understanding**

The team can ground their thoughts in something real. Not in abstract requirements. Not in vague descriptions. But in concrete, perceivable behavior.

The ticket is no longer a ghost. It is a substance.

**Better Communication**

The essence serves as documentation. It is interactive. It is testable. It is verifiable.

When the final implementation diverges from the essence, it is immediately visible. The team can correct it.

**Faster Implementation**

When the developer knows exactly what the substance is, they can build the accidents faster.

They do not need to guess. They do not need to interpret. They do not need to reinvent.

They just need to wrap the essence in the machinery.
